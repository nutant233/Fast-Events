Fast-Events 让 Forge / NeoForge 的事件总线变快。它是一个丢进 mods/ 就生效的 jar：不需要配置、没有依赖、 不用 Mixin、不修改任何其它模组。被它接管的每一次事件发布都变成一条直接、完全内联的调用链，而不是多态循环 —— 发布一个 事件的成本会降到接近你手写调用监听器的程度。

它加速的是所有模组的事件发布，不只是它自己：jar 会改写所有已加载类里的 post 调用点，所以那些大量发布事件的模组 （tick、方块/实体更新、capability 事件、屏幕事件）无需修改就能变快。

它解决什么问题

两种总线的分发逻辑都是这样：

for (EventListener listener : listeners) {
    listener.invoke(event);        // 一个调用点，要面对游戏里所有监听器实现类
}

这一个调用点会看到所有模组注册过的监听器实现，属于「超多态」（megamorphic）：JIT 一个都内联不了，于是每次监听器调用都要付 一次虚分派，再加上外层的包装层开销。在大整合包里，每 tick 的事件开销大部分就花在这上面，而不是你写的监听器逻辑。

它做了什么

  • 每个调用点一个生成的分发器。 某个 post 调用点第一次发布某个事件类时，会按该类当时的监听器数组生成一个 分发器：每个监听器一个字段、一条调用指令。于是每个调用点只见过一种接收者类型，能一路内联到监听器体里。
  • 没人监听就不构造事件对象。 如果某个事件类根本没有监听器，调用点上的 new Event() 会被短路， 连对象都不会构造。
  • 语义完全一致。 优先级顺序、phase 标记、取消、泛型类型过滤、异常处理全部与原生一致；生成的代码就是总线原本 会做的事的直线展开。
  • 缓存是活的。 监听器数组一变就重建分发器，所以「某个类已经在分发了之后才注册」的监听器同样生效。

安装

  1. 安装 Minecraft 1.21.1 + NeoForge 21.1.x、1.20.1 + Forge 47.x、1.19.2 + Forge 43.x、1.18.2 + Forge 40.x， 或 1.16.5 + Forge 36.x。
  2. 把对应的 jar 放进 mods/。（放在启动器 classpath 上也可以。）
  3. 就这样。没有配置文件，没有依赖，不需要任何额外设置。

客户端和服务端都支持，两边都能受益。开服的话装在服务端即可；连进来的客户端不装也没影响（装了会有一点额外收益）。

可选设置

只在排查问题时有用，正常游玩保持默认即可。

系统属性作用
-Dfastevents.guard=false关闭「没人监听就跳过 new Event()」的短路。
-Dfastevents.audit=true每次 post 核对缓存的监听器数组，并记录晚注册。
-Dfastevents.diag=true仅 1.21.1：记录那些经过「未被改写的路径」注册的监听器。

兼容性

  • NeoForge 21.1.x（1.21.1，event bus 8.0.x）与 Forge 47.x / 43.x / 40.x / 36.x （1.20.1 / 1.19.2 / 1.18.2 / 1.16.5，event bus 6.x / 6.x / 5.x / 4.x）。这些游戏版本的其它构建不保证。
  • 1.16.5 版编译为 Java 8 字节码，原版启动器自带的 Java 8 即可运行。
  • 不使用 Mixin，不使用 access transformer，也没有会和其它性能模组抢的 coremod 入口。它是一个 launch plugin，只替换 post/addListener 调用点。
  • 不修改 Forge、NeoForge 或 event bus 自身的类，也不碰其它模组的监听器与注册数据。
  • 随时可以删除 —— 它不会往存档或配置里写任何东西。
  • 不加速、仍走原生路径（因此不存在行为差异）：1.21 的 post(EventPriority, Event)；所有版本中总线引用在加载期 无法确定的 post 调用点。

常见问题

会改变监听器执行顺序，或者弄坏 @Cancelable 事件吗？

不会。生成的分发器严格按总线给出的数组顺序（也就是按优先级排好的顺序）访问监听器，取消判断的位置也与原生一致。依赖顺序或 「取消后提前返回」的模组行为完全相同。

只有少数几个模组的包有用吗？

收益与事件流量成正比。1.20.1 的大型整合包收益最明显；接近原版的实例也有一点收益，因为原版自己每 tick 也在发布事件。

会和其它性能模组冲突吗？

它不 patch 事件类，所以那些修改总线的观测/优化类模组不受影响。如果有别的模组也在替换 post 调用点，两个模组会各自 包装同一个调用点，结果依旧正确，只是多一层间接。

为什么这个功能不直接做进 Forge / NeoForge？

它需要在加载期改写所有模组的字节码，而加载器没法在不改变 API 契约的前提下对自己的分发循环做这件事。作为 launch plugin 就可以完全不碰 API 地做到。

整合包能用吗？

能。把与整合包游戏版本匹配的 jar 放进 mods/ 即可。整合包恰恰是收益最大的场景，因为每个事件类上的监听器数量会随 模组数增长。
